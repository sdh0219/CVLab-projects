# 第一部分 · 项目导览

## 1.1 这个项目是做什么的

**一句话**：FastAPI + Vue3 前后端分离的"城市应急指挥大屏"原型——把成都地区的公开真实数据（OSM 医院消防站点位、Open-Meteo 实况气象、公开报道的历史灾情）灌进 SQLite 数据库，用 ECharts 图表 + Leaflet 地图呈现"灾情态势/救援部署/物资调度/群众转移/AI 辅助决策"六大模块。

它最值得学的是**数据伦理设计**：拿不到的数字（真实库存、队伍人数、避难所容量）一律置 0 并标注"未公开"，**绝不编造**（`数据集\sources.md` 记录了每个数据的来源与许可）。这在"AI 大屏"满屏假数据的时代是稀缺的工程操守。

## 1.2 先体验功能（跑起来之前先知道长什么样）

六大页面（跑通后左侧导航切换）：

| 页面 | 亮点 |
|---|---|
| 指挥大屏 Dashboard | 成都地图 + 灾害/救援/避难/道路四类标记 + 3 个 ECharts 图 + 10 秒自动刷新 |
| AI 辅助决策 | 输入一段灾情文字 → 7 步工作流动画 → 抽取/风险评估/案例匹配/资源预测/方案/命令 |
| 灾情/救援/物资/转移 | 四个管理表格页（CRUD 增删改查） |

## 1.3 输入与输出

**吃进去（输入，`数据集\processed\` 下 7 个 JSON，全部公开数据）**：

| 数据 | 规模 |
|---|---|
| 历史灾情复盘 | 5 条（成都公开报道） |
| 消防站/医院点位 | 20+30 个（OpenStreetMap） |
| 避难所候选 | 12 个 |
| 主要道路状态 | 25 条 |
| 实况气象 | 1 条（Open-Meteo） |
| 物资目录 | 6 类（库存全为 0——未公开） |

**吐出来（输出）**：浏览器大屏（本地 3000 端口）+ SQLite 数据库记录 + AI 决策历史。另附自动生成的 API 文档页（Swagger）。

## 1.4 业务流程图

```
公开数据（OSM/Open-Meteo/新闻） → ETL 脚本 → SQLite（10 张表）
        │
        ▼
FastAPI 后端（8000 端口）
   /api/disasters 灾情 CRUD + 统计
   /api/rescue 队伍 + 最近救援点（Haversine）
   /api/materials 库存 + 需求测算（经验系数）
   /api/evacuation 避难所 + 转移方案（贪心分配）
   /api/ai/decision 七步 AI 工作流（无 Key 自动降级为规则模拟）
        │  HTTP API（JSON）
        ▼
Vue3 前端（3000 端口）：ECharts 图表 + Leaflet 地图 + Element Plus 表格
```

## 1.5 用到哪些技术（人话版）

| 技术名词 | 人话解释 |
|---|---|
| 前后端分离 | 浏览器页面（前端）和数据库服务（后端）是两个程序，通过 HTTP API 对话 |
| FastAPI | 现代最快的 Python Web 框架之一，自动生成交互式 API 文档 |
| REST API | 用 URL+GET/POST/PUT/DELETE 表达"对资源的操作"的风格 |
| SQLite | 单文件数据库，零安装零配置——学习与小项目首选 |
| ORM（SQLAlchemy） | 用 Python 类和对象操作数据库表，不写 SQL |
| Vue3 / Element Plus | 前端框架 / 现成的表格弹窗组件库 |
| ECharts / Leaflet | 百度开源图表库 / 开源交互地图库 |
| Vite | 前端开发服务器与构建工具 |
| Haversine | 球面两点距离公式（算最近救援点） |
| RAG | 检索增强生成（AI 决策里的案例匹配步骤） |
| Swagger / OpenAPI | 描述 REST API 的标准，FastAPI 自动生成可测试页面 |

# 第三部分 · 理解手册

## 3.1 背景：指挥舱的"真"与"假"

市面上很多"应急指挥大屏"演示里，库存量、队伍人数、受灾人数全是编的数字，看着炫、用着危险。本项目反其道而行：**能从公开渠道拿到的（点位、气象、公开灾情）才入库；拿不到的（真实库存、内部队伍数据）明确置 0 并标注"未公开"**。`数据集\sources.md` 逐条记录数据来源——这种"数据可溯源"的习惯，比任何炫技都值钱。

## 3.2 核心概念逐个讲

### 3.2.1 分层后端架构（backend\app\）

- `models/models.py`：10 张表的 SQLAlchemy 定义（灾情/队伍/物资/转移/避难所/人口/道路/气象/AI决策）；
- `schemas/schemas.py`：Pydantic 请求/响应模型——自动校验字段类型，错了直接 422 报错；
- `api/*.py`：6 个路由模块，`Depends(get_db)` 注入数据库会话；
- `services/ai_service.py`：AI 工作流；`data/import_real_data.py`：ETL。
**models→schemas→api 三层**是 FastAPI 项目的标准姿势。

### 3.2.2 ORM 与自动建库

`init_db()` 在启动时自动 `create_all` 建表——第一次运行就有一个空库；ETL 再填数据。SQLite 单文件、WAL 模式（并发读写优化）、零安装——学习项目的数据库最优解。

### 3.2.3 Haversine 最近救援点（api/rescue.py）

`d = 2R·arcsin√(...)`，R=6371km。按 60km/h 均速折算 ETA。前端某个灾情点想找最近的消防站——就是这一个公式的 API 化。

### 3.2.4 物资需求的经验系数（api/materials.py）

水 3 瓶/人/天、食品 2 份/天、每 100 人 1 份药品、每 4 人 1 顶帐篷——应急管理的行业经验值写成了代码。**领域知识就在这些常数里**。

### 3.2.5 七步 AI 工作流与降级（services/ai_service.py，519 行）

信息抽取 → 风险评估 → 案例匹配（RAG）→ 资源预测 → 处置方案 → 指挥命令，每步一个独立 prompt。**最值得学的是 L67-69**：整个工作流套 try/except，任何一步失败整体降级到 `_generate_mock_workflow()`（关键词规则+正则提数字的本地模拟）——**外部依赖挂了系统还能用**，这叫面向失败设计。

### 3.2.6 可选 Redis 的优雅降级（utils/cache.py）

缓存客户端延迟初始化+全 try/except：装了 Redis 就有 300 秒缓存，没装就每次直查数据库——**性能优化不绑架可用性**。

### 3.2.7 前端如何"活"起来

`api/index.js` 的 axios 实例统一 baseURL；Dashboard 用 `setInterval(loadData, 10000)` 十秒轮询（不是 WebSocket，但对原型足够）；地图用 Leaflet 的 divIcon 自绘"信标"标记。

## 3.3 代码精讲推荐路线

1. `backend\main.py`（40 行）——入口与路由注册；
2. `backend\app\models\models.py`——10 张表结构；
3. `backend\app\api\disasters.py`（最短 CRUD，50 行）——照它理解其余路由；
4. `backend\app\services\ai_service.py`——AI 工作流与降级；
5. `frontend\src\views\Dashboard.vue`（1100 行）——图表+地图+轮询三件套；
6. `frontend\src\api\index.js`——全部接口封装（20 个函数对后端路由）。

## 3.5 怎么读结果

- **AI 决策的"案例匹配"标签**：模拟模式返回的是内置历史案例文案；接了真实 LLM 才是语义检索；
- **数据库表**：用 VS Code 的 SQLite 插件打开 `emergency_command.db` 能直接看 10 张表。

## 3.6 思考题

4. 物资系数若按"每人每天"计算，灾情持续天数从哪来？（提示：目前是人工输入）
