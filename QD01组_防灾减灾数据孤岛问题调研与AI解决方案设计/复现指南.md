# 第一部分 · 项目导览

## 1.1 这个项目是做什么的

**一句话**：把防灾减灾领域散落在 7~8 个机构里的数据（气象、灾害声明、地震、人口脆弱性、消防站/医院、滑坡、道路）**清洗并融合成统一的数据表**，再用 Streamlit 搭一个"AI 风险评分 + 异常预警 + 资源调度"可视化看板。

它针对的是行业真痛点——**数据孤岛**：气象数据在 NOAA、灾害声明在 FEMA、地震在 USGS、人口脆弱性在 CDC……格式各异、互不相通。防灾决策需要把它们放在一起看，但"放在一起"这一步本身就是大工程。本项目以美国洛杉矶县（LA County）为对象，完成了从"七张异构表"到"一张统一事件表 + 一个决策看板"的全流程。

## 1.4 业务流程图

```
7 类异构数据（CSV / GeoJSON / 宽表）
        │  列名模糊匹配对齐（DATE/date/time 都认识）
        ▼

        │
        ▼

        │

        │
        ▼

```

## 1.5 用到哪些技术（人话版）

| 技术名词 | 人话解释 |
|---|---|
| 数据孤岛 | 数据分散在各机构、格式不通、无法联合使用 |
| ETL / 数据融合 | 抽取-清洗-统一格式-合并到一起 |
| Schema 对齐 | 不同表的同类字段名对上号（DATE vs date vs time） |
| GeoJSON | 存地理要素（点/多边形）的 JSON 格式 |
| 代表点提取 | 把多边形（如行政区）缩成一个中心点，方便统一处理 |
| 宽表/长表 | 一行多个测量列 / 一行一个测量值（pandas melt 互转） |
| Streamlit | 用纯 Python 快速搭建数据网页应用的最流行库 |
| Z-score 异常检测 | 某值偏离群体均值几个标准差，超过阈值报警 |
| 风险评分加权 | 多个指标按权重线性组合成一个综合分 |

# 第三部分 · 理解手册

## 3.1 背景：为什么"数据孤岛"是防灾的第一道坎

灾害来了，指挥官要同时回答：哪里雨最大（NOAA）、哪里宣布了灾区（FEMA）、哪里有滑坡史（州地调局）、哪里的人最脆弱（CDC SVI 指数）、最近的消防站在哪（OSM）。这些数据**分属不同机构、不同格式、不同更新频率**——把它们拼成"一张图"是每个应急平台的第一步，也是最费人力的一步。

本项目以洛杉矶县（全美人口最多县之一、山火地震洪水高发）为实验对象。7 个数据源全部是真实公开数据（`数据集\1 数据包\metadata\` 里保留了每个源的下载地址和字段字典）。

## 3.2 核心概念逐个讲

### 3.2.1 Schema 对齐：让 DATE / date / time 握手

不同机构对同一概念起不同名。`find_col()`（main.py L144-156）做大小写无关 + 子串模糊匹配：找"日期"列时依次尝试 DATE/date/time/event_date…这是所有数据融合项目的第一步杂活。

### 3.2.2 宽表熔成长表（melt）

NOAA 气象原始表一行放 TMAX/TMIN/PRCP 多个测量列（宽表），不利于统一处理。`clean_weather` 把它"熔"成长表：一行一个测量（indicator 列说是什么指标，value 列是数值）。**pandas 的 melt/宽长互转是数据分析基本功。**

### 3.2.3 GeoJSON 代表点提取

行政区是多边形（一串坐标圈起来），地震是点。要统一到一张表里，把多边形缩成"中心点"（所有顶点坐标取均值，L184-213 递归处理嵌套坐标）。牺牲精度换取统一性——典型的工程取舍。

### 3.2.4 统一事件表：本项目的"合龙"时刻

`build_unified_hazard_events()` 把三类灾害源拼成同构 10 列：地震的"严重度"填震级、FEMA 填声明级别、滑坡填置信度——**不同量纲的严重度共处一列并注明来源**。这一步完成，"孤岛"就变成了"一张表"。

### 3.2.5 看板里的"轻量 AI"（app.py）

- **风险评分**：`0.5×灾害分 + 0.3×人口脆弱分 + 0.2×资源缺口分`（app.py L394-398），阈值 75/55/35 分红/橙/黄；
- **异常预警**：按指标分组的 Z-score——某县今日降雨偏离该县历史均值 ≥2 个标准差就报警（≥3 红、≥2.5 橙、其余黄）；
- **资源调度表**：灾害点附近的消防站/医院匹配清单。
全部用 pandas/numpy 实现，没有一个大模型——**"AI"的门槛没有想象中高，关键是指标设计**。

### 3.2.6 数据源状态表：诚实的元数据

`data_source_status.csv` 记录每个源"有多少条、状态、最后更新"。缺数据的源标 MISSING 而不是假装存在——数据工程的可信度全靠这种诚实。

## 3.4 动手改一改

**练习 1（入门）· 改风险评分权重**

## 3.5 怎么读结果

- **平台总览页**：7 个数据源的记录数、时间覆盖——孤岛现状一览；
- **风险评分页**：按县/区的综合风险分排序——注意分数依赖三个分项的量纲归一；
- **异常预警页**：Z-score 超阈的指标清单——注意"该县的历史"是参照系，干旱县下 20mm 雨可能就报警；
- **数据源诊断页**：每个候选路径的 ✅/❌——排障第一站。

## 3.6 思考题

1. 统一事件表把震级、声明级别、置信度放进同一个"严重度"列，量纲不同公平吗？你会怎么改进？
2. 代表点把多边形缩成点，什么时候这个简化会误导决策？
3. Z-score 假设数据近似正态。降雨量的分布是正态的吗？更适合的统计量是什么？
4. 如果 FEMA 只有 16 条声明记录，用它做统计可信吗？小样本源该怎么用？
